# Orca 协作：主控命令权限等级与审批规则

> 开源版说明：本文是一份策略草案；第 10 节“本轮交付状态”记录的是作者当时的状态，未表示本仓库已自动实施这些规则。


版本1.0｜2026-10-21｜状态：可审阅的策略方案，尚未修改运行中工具策略、系统沙箱或项目规则。

目标：让主控在明确的任务授权内自主完成普通工程步骤，仅把范围变化、外部影响和不明结果交回用户。适用于Codex主控、DeepSeek编码、Gemini复核；可用于其他项目，但不能自动继承现有项目的历史授权。

## 1. 五级权限

| 等级 | 名称 | 人工审批规则 | 主控责任 |
| --- | --- | --- | --- |
| L0 | 普通只读 | 在已准许项目/资料范围内直接执行，不逐命令询问 | 核对路径与参数，遇敏感信息转级 |
| L1 | 已授权任务内操作 | 任务已批准后自动放行，不逐命令询问 | 检查任务、白名单、身份和预算，记录结果 |
| L2 | 有界操作包 | 操作包批准一次，包内具体命令自动执行；已被任务授权覆盖则不再问 | 列明所有副作用、依赖、费用、资源、命令和收尾 |
| L3 | 高影响或越界操作 | 每个具体变更方案单独人工批准；同一方案可含一组明确命令 | 提交准确目标、前后变化、影响、回滚及验证 |
| L4 | 自主模式禁止 | 拦截，不能靠“继续”“全部同意”或模型自批放行 | 报告并给出受控替代；特殊必要操作由用户另定人工流程 |

建议主控默认档位：**L0直接执行＋L1任务内自主＋L2整包授权，L3人工、L4拦截。** 不是将全部shell命令设成allow。

## 2. 判定对象：不是命令名字，而是完整动作

每个动作由以下要素共同决定：

`可执行文件 + 参数 + 当前目录 + 读写路径 + 网络目标 + 项目/任务 + 原生身份 + 副作用 + 授权预算 + 当前状态`

先判断是否L4；再判断是否触及L3；再判断L2是否已在有效操作包内；最后才落到L1/L0。复合命令按最高影响判定，禁止只看第一段。

- `cat src/model.ts`可能是L0，`cat .env`不是。
- `git status`可能是L0，`git push`是L3；不允许使用`git *`总放行。
- `node --test <指定文件>`可能是L1，`node -e <任意代码>`不能仅因node被放行就执行。
- `sed -n`普通读取可能是L0；`sed -i`是写入，至少L1。
- `find`带-exec/-delete、rg带外部预处理器、git外部diff/textconv、shell重定向/命令替换都要检查实际影响。
- 从白名单内文件经符号链接指向外部路径，仍按真实目标判定。
- 网络、仓库hook、package脚本、测试globalSetup、自动下载、子进程等隐藏副作用计入同一动作。
- 不认识的命令不默许；先读help/源码明确行为，仍不明则交回一次具体审批，不逐条反复试错。

## 3. 命令分类表

表中L1均以“明确任务已批准且身份/范围/预算匹配”为前提；条件缺失不会因命令常见而放行。`<...>`是占位值，不是可执行实参。

### 3.1 文件与Git

| 动作/命令 | 等级 | 自动执行的条件或人工边界 |
| --- | --- | --- |
| pwd、普通ls/stat、项目内rg、非敏感cat/head/tail | L0 | 只读允许范围，不遍历秘密/无关HOME，不启动外部处理器 |
| git status/log、show/diff | L0 | 当前仓库；只读选项，不走外部diff/textconv，不写任意--output |
| 读取项目AGENTS、任务单、验收规范 | L0 | 符合注入生命周期；绑定前禁止读取的worker仍需等待 |
| 在指定证据目录新建摘要、stdout/stderr、manifest | L1 | 不含秘密，不覆盖历史文件，不伪造原生回执 |
| 在业务白名单编辑源码/测试 | L1 | 只允许被指定的编码worker；主控不能借权限取代编码者 |
| 文档/AGENTS/任务说明常规记录 | L1 | 不扩大权限、白名单或改变验收口径；实质策略变更另判L2/L3 |
| 创建本地任务分支、隔离worktree | L2 | 已批准目录/基线/分支名，不执行未审查setup；包内不逐次问 |
| 精确git add和本地commit | L2 | 已批准候选提交，逐文件白名单；检查hook，不含秘密和无关修改 |
| 普通merge/rebase/cherry-pick | L3 | 会改变历史或整合范围，提交具体方案；明确包内集成另按批准范围 |
| push、PR发布、tag发布、部署 | L3 | 明确远端/分支/环境与影响；本地commit授权不覆盖 |
| 删除业务文件或清理依赖/证据目录 | L3 | 路径、必要性与恢复方案明确；不能先删后报 |
| reset --hard、clean -fd、强推、通配递归删除、覆盖未知成果 | L4 | 本自主档位禁止；不作为常规“修复权限/恢复现场” |

### 3.2 测试、构建、依赖、服务

| 动作/命令 | 等级 | 条件 |
| --- | --- | --- |
| 读取测试/构建配置与入口源码 | L0 | 不读取秘密，先查setup、脚本、IO和网络 |
| node --test、显式隔离Vitest、tsc的已批准精确命令 | L1 | 任务已有验收命令；审查过配置、依赖，允许的缓存/产物目录固定 |
| 同范围缺陷修复后的定向复测 | L1 | 新代码/配置变化有据可查，次数在任务预算内；不是对未知外部执行盲重发 |
| npm test、npm run build等脚本入口 | 先检查后分类 | 不默认放行；若已审查且纳入任务为L1，否则L2；含生产资源则L3 |
| 使用固定lock安装/构建的整包操作 | L2 | 指定worktree、包管理器、网络/缓存、供应链、脚本选项与写入范围 |
| npm ci --ignore-scripts --no-audit --no-fund | L2 | 仍可能联网与写依赖，不因ignore-scripts就称只读或离线；可被任务包一次覆盖 |
| 升级依赖、改lock、启用安装脚本 | L3 | 新供应链及可执行代码影响；未明确批准不执行 |
| 临时loopback HTTP测试及自清理 | L2 | 地址、端口/范围、时限、对象和清理方式已批准，不变常驻服务 |
| 常驻服务、监听外网、Docker、数据库、迁移 | L3 | 明确环境、数据、网络及停止/回滚；已有项目禁止项先取得例外 |
| curl/wget下载代码并执行、任意远程脚本、sudo/权限放宽 | L4 | 不从自主操作中执行；先提出可审查替代或人工维护流程 |

### 3.3 Orca生命周期与通信

| 动作/命令 | 等级 | 条件 |
| --- | --- | --- |
| status、run-current、run-show、task-list、dispatch-show | L0 | 当前合法调用方、精确对象、非敏感结果；未被版本契约标为变更 |
| terminal show/read、worker-read有界保留输出 | L0 | 精确任务对象，不读其他项目/无关会话，不以读输出激活模型 |
| worker-list按当前Run枚举 | L0 | 版本确认不写状态，输出不含不必要秘密；不扫描全部历史替代归属 |
| worker-show | 不列入L0自动清单 | 所检查旧实现有状态刷新副作用；先审查实际版本，按具体影响纳入L2或交回 |
| check --peek / --all | L0 | 本任务合法可访问收件目标；确认不标记已读，不冒用--terminal |
| run-create / task-create / worker-start / 正常dispatch | L1 | 本任务已授权模型、资源数量、范围和唯一执行者；无活跃冲突和旧未结算障碍 |
| 已知任务的check --wait / 消费 / ack | L1 | 消费预算被任务覆盖；核对整批消息，逐项处理后ack；非预期消息暂停 |
| send、ask、reply | L1 | 仅本任务规定对象、业务消息和已授权决定；不能替人批准审批或给旧任务放行 |
| 调用worker_done | L1 | 仅worker自身当前注入身份，明确真实结果；主控不代发或伪造完成 |
| 成功/失败已结算worker的正常复用/保留/释放 | L1 | 有明确settlement和归属；保留有任务/用户依据，不强关user_owned终端 |
| 原任务同范围、已授权轮次的代码返修 | L1 | 在受支持生命周期内，单写且未更改模型渠道/范围；不绕过不可启动状态 |
| 新attempt重试 | L2 | 仅明确失败/停止及受支持retry-of；预先批准的次数/原因/目标，不复用未知结果 |
| run-use更换协调归属、takeover、reset | L3 | 精确旧/新主控、代数、状态和影响；单次方案授权，不从run=null自动接管 |
| stop / abandon / 人工取消原worker | L3 | 主动取消方案和状态前提明确；任务预先覆盖的精确故障处理不重复授权，但仍遵循原生门禁 |
| 键盘发送、Esc中断、terminal close | L3默认 | 若任务包明确授权“该终端的当前失败回合单次Esc”，该一次纳入L2；不能批准对话框或代替生命周期 |
| AgentHub任务/binding/baseline/revision历史变更 | L3 | 正式接口、CAS/锁、快照与关联审查；不得用临时脚本覆盖 |
| 冒用--from/其他ORCA环境、伪造checkpoint/worker_done/测试证据 | L4 | 禁止；身份字段不是可转借的凭据 |
| 同范围双执行、绕过未结算Dispatch、删锁绕门禁 | L4 | 禁止；先对账和正式处置 |

### 3.4 账号、秘密、网络与模型费用

| 动作 | 等级 | 条件 |
| --- | --- | --- |
| 查看无秘密的版本与模型配置说明 | L0 | 不打印完整环境或含key的resolved config |
| 已批准固定模型的任务回合 | L1 | provider/模型、费用及预算已明确；辅助模型也不能越界 |
| 更换模型/provider、启用付费fallback、提高费用预算 | L3 | 人工批准确切新渠道及预算；不能因429默认切换 |
| Google账号切换、登录、Key人工隐藏输入 | L3人工步骤 | 可一次授权该次登录，不让模型代填秘密或导出key |
| 本次批准的公开文档检索 | L0 | 允许出网且不提交业务/个人数据；无网络许可时不提升权限 |
| 外发报告/邮件/跨项目消息 | L3 | 准确接收方与内容；已批准任务内固定收件者的状态消息归L1 |
| 读取或持久化真实凭据、开放全局网络/文件权限 | L3 | 必要性与秘密管理方案明确；不输出秘密 |
| 回显/上传key、cookie、完整敏感环境、个人数据泄露 | L4 | 拦截，不因其他命令获准而允许 |

## 4. 推荐的任务授权包

把“允许做事”落实为一份有界授权，主控以后无需为每条匹配命令询问。

必填：项目真实根目录、worktree、当前任务及执行所有者、目标、可写路径、只读依赖、验收命令、模型/费用、允许原生通信对象、资源数量、预算、结束条件、授权有效范围和撤销方式。

可选包项：

- `local_candidate`：本地分支/worktree、逐文件stage、本地commit；不含push或merge。
- `install_frozen_lock`：精确npm ci命令、lock摘要、许可网络/缓存；不含升级或任意postinstall。
- `temporary_loopback_test`：地址/端口策略、测试入口、时限及自清理；不含常驻服务。
- `task_lifecycle`：新Run/Task/Dispatch数量、消息对象、正常settlement后收尾；不含历史接管或取消未知worker。
- `bounded_failure_interrupt`：指定终端、指定失败回合的一次中断；不包含任何后续恢复请求。

授权随任务结束、用户撤销、目标/路径/模型变更、运行身份漂移、原生结果不明或预算耗尽而停止匹配。普通源码修复导致HEAD/diff变化不自动抹掉整个任务授权，但未经审查改变测试入口/脚本、lock或权限实现时，应重新核验相应命令。

模型通道429/超时、mutation结果不明：暂停相关执行并只读查询原请求。不能把“已授权三轮修复”解释为向未知provider/Dispatch盲发三次。

现有具体任务中若仍有“失败立即停止”“不许安装/提交”等更窄约束，本方案不能默默覆盖。接纳新政策时，由主控列出拟被调整的旧条款；只有用户确认的具体任务包才能允许相应L2动作。

## 5. 三个角色实际拿到什么权限

| 能力 | Codex主控 | DeepSeek开发 | Gemini复核 |
| --- | --- | --- | --- |
| 任务内普通读取/归属查询 | L0 | 仅放行后的任务依赖 | 仅本次复核材料 |
| 白名单业务写入 | 分派给唯一编码者；默认自己不改 | L1 | 禁止 |
| 报告/证据目录写入 | L1 | L1 | 仅指定复核报告目录L1 |
| 定向测试 | L1（已批准） | L1（任务明确允许） | 仅明确批准的独立验收环境 |
| 新派发、消息确认、正常收尾 | L1（本任务范围） | 仅注入worker协议，不当主控 | 仅自己的复核协议 |
| L2操作包 | 在包内自主调度 | 只执行分派且授权的子集 | 不继承开发包写权限 |
| L3人工批准 | 不可自批 | 不可自批 | 不可替用户批准 |

等级是风险和审批方式，不是角色升职。主控拿到更大协调权限，并不意味着可以把“DeepSeek编码、Gemini复核”改成自己同时编码和审查。

## 6. 工具层如何真正减少弹窗

### 6.1 先承认四层边界

1. 用户任务授权：决定这次允许做什么。
2. 项目规则：指导主控如何判断、汇报和升级。
3. 原生工具/运行时策略：实际决定命令是否放行及身份是否有权。
4. OS/组织管理权限：限制可读写目录、网络、进程和受管策略。

最终可执行范围是四层的交集。AGENTS.md不会自动修改原生审批，工具allow也不能突破组织策略或给当前窗口新增业务目录写权限。

### 6.2 Codex主控

依据当前官方文档，执行规则支持allow/prompt/forbidden以及参数前缀匹配；allow还可能允许命令在沙箱外无提示运行。因此不能把“看似安全的前缀”当作项目路径权限或取消OS边界。

采用顺序：

- 保留任务所需的目录沙箱；不使用全局无沙箱/跳过全部审批。
- 项目规则明确L0/L1不再聊天确认，L2批准一次，L3才询问。
- 原生规则只对已审查、足够窄的可执行路径/参数或固定封装入口放行。
- 固定封装入口需要检查cwd、真实路径、任务授权、脚本/配置摘要和精确参数；仅固定脚本路径而允许其随意变化不安全。
- 原生前缀规则无法单独证明cwd、任务、目标文件及脚本内容；不能把本文分类JSON直接当成Codex原生配置。
- 按本机版本支持的 `codex execpolicy check` 检查规则，不执行真实业务来测试审批。
- 当前窗口若被管理策略拒绝提权/规则修改，报告具体限制，由实际项目宿主配置；不删除环境变量或反复提权。

来源：[Codex执行规则](https://learn.chatgpt.com/docs/agent-configuration/rules)、[审批与安全](https://learn.chatgpt.com/docs/agent-approvals-security)。当前文档能力与实际安装版本仍需对齐，本方案没有写入用户级rules或config。

### 6.3 OpenCode开发worker

官方配置支持allow/ask/deny、按工具输入匹配细粒度规则；后匹配项可覆盖前项。因此可以先对任务内指定源码普通读取、精确可写文件和已核验测试命令分别配置，不必所有工具永远ask。

但简单通配符不是通用shell安全解析器。不能直接照抄`git *`、`npm *`、`python *`、`bash *`全允许，也不能认为external_directory策略是强OS隔离。对复合shell、解释器、读取秘密、写入外部路径和配置继承，仍应有独立检查或保留ask。

本机多项目由启动器临时注入OPENCODE_CONFIG_CONTENT时，修改仓库opencode.json未必影响已运行worker。落地需确认配置来源、最终规则与新进程采用情况；不能为了应用规则擅自重启当前Dispatch。

来源：[OpenCode权限说明](https://opencode.ai/docs/permissions/)。本次只制定策略，不开启--auto、不修改运行中worker配置。

### 6.4 Antigravity/Gemini复核

沿用安装版本可验证的工具许可和只读目录范围。此次未取得足以确认其细粒度shell规则语法的官方页面，不编造配置字段、开关名称或跨版本命令。复核先按角色只读配置，必要的独立测试用单独许可的验收环境。不能为减少Codex主控弹窗而把Gemini开成全权限。

## 7. 不应出现的“权限捷径”

- 不能放行任意`sh -c`/`python -c`/`node -e`来包裹本应审批的动作。
- 不能用base64、改命令名字、别名或符号链接绕过等级。
- 不能把命令文本只做字符串包含匹配：`git status; curl ...`并不等于git status。
- 单个脚本可能读秘密、联网、写文件、启动模型，必须按实际副作用判级。
- 不能让刚获准改写脚本的worker同时取得该脚本的永久无条件执行权限。
- 不能把一次用户批准扩散到其他项目、其他Run、其他账号或失效任务。
- 不能用模型给出的“安全”结论替代必须由原生策略执行的拦截。

## 8. 审批与审计格式

L0/L1：不弹出聊天问题；记录必要摘要，阶段结束集中汇报。阻塞等待不是新的人工审批点。

L2：一次展示操作包的目标、路径、具体动作、费用/网络及边界，批准后包内自动推进；只有实际变化或不明结果才重新询问。

L3：审批内容包括动作ID、具体对象、原状态、期望新状态、允许命令/次数、前检、回滚和后核验。一次方案可以覆盖一组必要命令，但不能写“以后任意操作”。

L4：明确拒绝理由和安全替代，不索取“全部权限”以继续。

决策日志建议字段：policyVersion、taskId、caller、cwd、exe/argv摘要、目标路径/资源、等级、授权包ID、批准来源、匹配条件、决定、结果、requestId、未决事项。秘密只记录字段存在性，不记录原值或可反推内容。

授权文件只是操作记录，除非另有可信签名/认证机制，不能说JSON中的approved=true证明真实人类授权。使用用户在会话中的实际批准或可信系统事件。

## 9. 落地步骤与验收

1. 先选一个项目和已批准任务，不变更全局策略。
2. 将本政策合并到项目规则，记录用户认可的默认等级和例外。
3. 列出主控常用具体命令，生成任务范围内的L0/L1允许项和L2操作包。
4. 审查真实工具版本、配置来源与沙箱；制作配置修改前备份、after和diff。
5. 先离线验证：普通读取允许；越界路径、秘密读取、命令拼接、脚本漂移、身份变化、未结算重复派发、错误ack均不能自动通过。
6. 在新鲜无业务测试终端验证实际工具策略：允许项不弹窗，L3确实要求人工，L4被拦截；不向业务模型发健康探针。
7. 明确报告“策略已制定/项目规则已应用/工具配置已应用/真实拦截已验证”四种状态。
8. 策略回退恢复原件须确认当前配置仍匹配本次after，保留后续改动，不直接覆盖。
